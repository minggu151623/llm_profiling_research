# Which branch-prediction claims remain open?

**GraalSP and GraalNN already estimate branch probabilities from static compiler information.** The 2025 Method Names abstract establishes a precedent for lexical embeddings in method-hotness prediction. The same research group now describes work on method-signature embeddings for branch probabilities. Our working question is how much a small language model adds beyond structural and lexical baselines on original Java bytecode, across unseen projects and under workload shift. This three-publication review leaves any priority claim open. [GraalSP](https://doi.org/10.1016/j.jss.2024.112058) · [GraalNN](https://doi.org/10.1145/3696443.3708958) · [Method Names, p. 36](https://simpozijum.matf.bg.ac.rs/KNJIGA_APSTRAKATA_2025.pdf#page=36) · [PLATO, “Embeddings”](https://plato.matf.bg.ac.rs/?content=research_graalvm_sprof)

| Candidate claim | Existing evidence | Evidence our project would need |
| --- | --- | --- |
| Static bytecode features can predict branch probabilities | GraalSP uses XGBoost with Graal IR features. GraalNN learns block representations with GraphSAGE and includes calling context during inlining. [GraalSP note](reading_notes/graalsp.md) · [GraalNN note](reading_notes/graalnn.md) | Measure error against taken/fall-through counts at original bytecode offsets. Any direct Graal comparison needs matched IR edges, edge direction and mapping coverage. |
| Identifier semantics improve prediction | The published abstract compares method-hotness classifiers with and without GloVe names. The authors' lab also describes an **in-progress** manuscript, *Profiling Beyond IR*, adding method-signature embeddings to GraalNN branch prediction. Its publication status and independently reproducible results are **UNVERIFIED**. [Method Names note](reading_notes/method-names.md) · [Lab project description](https://plato.matf.bg.ac.rs/?content=research_graalvm_sprof) | Within each test fold, compare structural, identifier-only, structural-plus-lexical, and SLM models on identical branch/workload rows. Mask identifiers consistently, including class, method, field and call-site references. |
| Gains transfer to unseen code and workloads | GraalNN evaluates multiple benchmark suites. The verification here establishes no directly comparable branch-level MAE value under our proposed split. [GraalNN, §§3–4](https://doi.org/10.1145/3696443.3708958) | Hold out projects, remove duplicate code, and report per-project results. For workload shift, compare measured labels on the same compiled branch across workloads while holding its static prediction fixed. |
| Better probabilities imply faster Java programs | The two Graal studies report runtime changes in their own Native Image pipelines. The 2025 Method Names abstract reports a binary-size/runtime trade-off. [GraalSP](https://doi.org/10.1016/j.jss.2024.112058) · [GraalNN](https://doi.org/10.1145/3696443.3708958) · [Method Names](https://research.matf.bg.ac.rs/handle/123456789/3037) | This pilot measures direction, counts and coverage. Compiler speedup would require a separate optimization experiment and joint scope review. |

## What changes a paper claim?

A useful negative result would quantify where a lexical baseline matches an SLM and where workload variation dominates the measured error. Before either researcher claims novelty, extend the review to classical branch heuristics and binary-level profilers, check the status of the signature-embedding manuscript, and record its evaluation protocol if a citable version appears. GraalSP verification currently covers publisher excerpts and first-author material. The linked research-group page lists a related thesis for follow-up.
